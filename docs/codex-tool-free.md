# Verified Codex chat transport

Tested with the authenticated local `codex-cli 0.166.0` on macOS arm64, 2026-11-04. This replaces the earlier blanket provider disable. No CLI upgrade, login change, or user config mutation was performed.

## Investigation

`codex --help`, `exec --help`, `features list`, `login status`, `app-server --help`, and generated experimental app-server JSON schemas were inspected. The local user config was inspected without retaining credentials or MCP headers; only its safety-related shape is recorded in `user-config-shape.json`. Help output is retained in [security-evidence/codex](security-evidence/codex/). The installed CLI supports `exec --ignore-user-config`, `--ignore-rules`, `--ephemeral` and stdin prompts. Profiles layer configuration rather than remove tools, so none is used. `-c key=value` parses TOML; false values for `tools.update_plan` and `tools.experimental_request_user_input` fail configuration parsing: these require `.enabled=false`.

The public [configuration reference](https://developers.openai.com/codex/config-reference/) was consulted; the installed executable and matching source are authoritative for this verification. Matching source was fetched to `/tmp/vstudy-codex-investigation`, tag `rust-v0.166.0`, commit `6ff1e1c` (not the repository's newer main). Relevant sources:

- [tool registration](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/core/src/tools/spec_plan.rs): shell registration checks `features.shell_tool`; apply_patch registration independently checks model metadata. Utility, collaboration and hosted tools have separate controls.
- [model metadata](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/protocol/src/openai_models.rs): `shell_type`, `apply_patch_tool_type`, `experimental_supported_tools`, `tool_mode`, and `multi_agent_version` affect tool exposure.
- [request serialization](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/core/src/client.rs): Responses Lite omits top-level `tools` and instead emits an `additional_tools` input item when tools exist. Both surfaces must be checked.
- [permissions](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/config/src/permissions_toml.rs): named profiles/default_permissions can describe deny/read permissions. `sandbox_workspace_write` provides writable roots, network access and temporary-root exclusions, not a no-tools switch. An empty cwd with read-only sandboxing does not remove shell or filesystem-reading authority. No claim of deny-read protection is made here.

T3 Code was cloned outside this repo to `/tmp/vstudy-t3code-investigation`, commit `b7ab02e0f6077a72cadfa5c9a40db4db67bc325f`. Its `apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts` uses app-server, enables planning, injects MCP servers, and supplies per-thread config/sandbox/approval policy. It is an agent transport, not evidence of a tool-free chat setting. Installed app-server `thread/start` supports sandbox, approvalPolicy, config, baseInstructions, developerInstructions and experimental dynamicTools. An empty dynamicTools list removes only client-supplied tools. Base/developer instructions are language guidance; they do not remove native tools. No app-server transport was adopted.

## Mechanism

Every chat uses an empty private temporary HOME/CODEX_HOME/cwd. Only `auth.json` is copied from the real Codex home, with mode 0600; user/project config and execpolicy rules are ignored, project instructions and host skill discovery disabled, sessions ephemeral. State and the auth copy are deleted after completion, cancellation or failure.

The app supplies a minimal model catalog with the selected slug, `shell_type=disabled`, `apply_patch_tool_type=null`, no experimental tools, direct tool mode, and no model-selected multi-agent mode. Each slug, including unknown future slugs, receives this same metadata instead of the CLI's fallback agent metadata. Effort/service-tier choices continue to come from the existing discovery catalog. Explicit config disables shell, view_image, planning, user-input, agents, goals, image generation, apps, plugins, browser/computer tools, Code Mode, shell snapshots, hooks, memories, skill discovery and web search. See `codex.ts` for the exact audited argv values.

The process is launched with argv arrays through `/usr/bin/sandbox-exec` and the literal profile `(version 1)(allow default)(deny process-fork)`. The profile contains no interpolated paths or shell text. Its purpose is to enforce zero child processes, including Code Mode and shell helpers; its real test shows a shell's attempted child fails with `Operation not permitted`. This is stronger than sampling the process tree, which could miss short-lived children. Existing detached process-group SIGTERM/SIGKILL and Stop handling remain in use.

This is native tool removal, supplemented by a process-creation restriction. The wrapper is **not** a least-privilege filesystem or endpoint-only network sandbox. The CLI itself retains filesystem/network access for its implementation and authentication. Restricting all native reads/network with a separate general-purpose profile was not needed for the chosen mechanism and was not verified. A hypothetical compromised CLI could still read files or send data directly without spawning children. Same-user replacement of the binary/cache remains outside the threat boundary.

## Proof and runtime gate

`VSTUDY_CODEX_LIVE=1 pnpm --filter @vstudy/desktop exec vitest run src/main/providers/codex.test.ts` runs the real authenticated canary test; it skips by default and when the CLI/login is absent. It creates a secret outside the cwd and a second HOME-like canary, supplies their paths but never their secret values to the prompt, includes a document-selection injection, and asks for reads, a home listing, a write, curl, patch, MCP, web, image and agent tools. It checks that neither secret appears, the requested file is absent, and no item outside assistant-message/reasoning types appears. A native sandbox test enforces no child processes. Raw passing events are retained in `apps/desktop/src/main/providers/fixtures/codex-tool-free-live.jsonl`; no secret or credential is retained.

A separate local capture endpoint receives a real CLI request using the same catalog/settings and Responses Lite serialization through a custom capture provider. It asserts both top-level tools and additional_tools are absent. This corroborates tool construction; it is not a capture of encrypted production traffic or an independent test of every hosted-provider capability. The real ChatGPT-backed adversarial turn is the production-provider check. Eleven targeted tests cover the live proof, request capture, native fork denial, event allowlist, missing CLI and unaudited executable; see [live evidence](security-evidence/codex/live-tests.txt).

At provider startup, the app requires macOS, sandbox-exec, exactly CLI 0.166.0, and a passing authenticated canary check. Successful proofs are cached against the executable SHA-256, app version and the complete catalog/config/profile settings. A changed executable or safety setting invalidates the proof. Failures remain unavailable for that adapter instance; restart after fixing login. Detection, model listing and streaming all share this gate. Failure displays `Unavailable: could not verify tool-free mode` plus a reason. Streaming also rejects unexpected item types, including command_execution, file_change, mcp_tool_call and web_search, even without a final newline. Event rejection is defense in depth, not a substitute for removing tools before execution.

A finite adversarial prompt cannot establish model obedience. The enforceable claim rests on the audited version's tool registration, supplied catalog/config, process-fork denial, and observed live/request evidence. Other CLI versions, keychain-only auth, other operating systems, live quota exhaustion and signed/notarized packaged execution remain unverified.

## Final application verification

Typecheck, lint, production build and the normal suite passed (50 files; 258 tests passed, six opt-in tests skipped). The separately live-enabled Codex suite passed all eleven tests. The final compiled Electron app imported a real Markdown document, selected Codex/GPT-6.1-Sol through the model picker, received and persisted “Codex chat is working.”, displayed reported token usage, and stopped a second live request. See [screenshot](security-evidence/codex/chat.png), [chat log](security-evidence/codex/chat.txt), and [command logs](security-evidence/codex/).

All 22 e2e scripts have passing final results in [the results manifest](security-evidence/codex/e2e-final-results.json). The initial complete sweep had 20/21 passing: Welcome performance recorded scroll/demo dropped frames and long frames while other test work was running. That failure is retained as [contention evidence](security-evidence/codex/performance-contention.json); it is not represented as a pass. After all other own test/build work stopped, the isolated rerun passed with twelve entrances, zero dropped frames, zero long frames, zero CLS and zero offscreen animations in both themes ([raw metrics](security-evidence/codex/performance-isolated.json)). The new live Codex e2e is the 22nd script. Historical design-review evidence regenerated by e2e scripts was restored; this run's results live separately here.

No signing/notarization/package re-verification, other CLI versions, native accessibility review, keychain-only Codex login, or real quota/rate-limit exhaustion was performed. Existing usage/rate-limit parsers and error classification remain in the normal test suite; the live screenshot proves usage, not a quota event.
